并发模型
三处 review 修复 · H1 + C2 + C1

串起：并行多工具调度 + per-trace 审计锁 + 三处安全 review 修复。 配套日志 kyagent/agent/core.log、kyagent/audit/logger.log、kyagent/executor/proxy.log。

1 为什么需要并发

LLM 一轮可能同时发起多个 tool_use（"先查进程，再看端口，再看磁盘"）。无依赖的只读感知工具：

SERIAL
总耗时 = ps + ss + df
完全串行：三次 syscall 顺序等
PARALLEL
总耗时 ≈ max(ps, ss, df)
理论上能省 60-70% 的尾延迟

前提：确保并发不引入安全或正确性问题。

AND

3 _is_parallel_safe — C2 修复后的五重判定

agent/core.py:217
def _is_parallel_safe(self, tu):
    tool = self.registry.get(tu.name)
    if tool is None:                                # 1. 工具必须存在
        return False
    if not tool.read_only:                          # 2. 必须只读
        return False
    if self.guardrail.llm_reviewer is not None:     # 3. ★ C2 第一道防线
        return False
    try:
        cleaned = tool.validate(tu.input or {})
        argv = tool.build_argv(cleaned)
    except ToolError:                               # 4. 参数必须能过
        return False
    verdict = self.guardrail.check_argv(argv, declared_risk=tool.risk_level)
    return verdict.decision is Decision.ALLOW       # 5. 预检必须 ALLOW

5 H1 修复 · _jsonl_fp TOCTOU 防御

5.1 风险（修复前的错误模式）

❌ 错误模式
if self._jsonl_fp is not None:            # 第一次解引用
    line = json.dumps(...)
    with self._jsonl_lock:
        self._jsonl_fp.write(...)         # 第二次解引用 ← BOOM

close_file() 同时持 _jsonl_lock 把 _jsonl_fp 置 None。TOCTOU 窗口：

1. event() 拿到 _jsonl_lock（即将写）
2. close_file 等 _jsonl_lock
3. event() 写完释放锁
4. close_file 拿锁，置 None，释放锁，flush+close
5. event() 第二次进锁里 self._jsonl_fp.write(...) → NoneType.write 报错

5.2 修复

✓ 正确模式
if self._jsonl_fp is not None:            # 仅作 fast-path 短路
    line = json.dumps(...)
    with self._jsonl_lock:
        fp = self._jsonl_fp                # 锁内 capture 到 local
        if fp is not None:                  # 锁内二次判空
            fp.write(line + "\n")           # 用 local 引用写
1
外层 if 仅作 fast-path 短路：跳过 json.dumps 这种比较贵的操作
2
真正解引用 + 写入移进 _jsonl_lock 内，先 capture 到 local fp 再判空
3
JSONL 关闭后再来的 event 静默丢弃该行，不抛异常
4
SQLite 仍是权威审计源，丢失的 JSONL 行是冗余通道，不影响回溯
NOTE
当前是否会触发？ 不会 —— agent.shutdown 不连带调 audit.close_file，ThreadPoolExecutor 的 _python_exit 优先于 user atexit，atexit 跑时 worker 早已 join。 但代码模式本身错误，是 footgun。任何后续添加的 graceful shutdown 把 close_file 挪到 worker 仍存活的窗口就会立刻活。

6 C2 修复 · 预检 ≠ 内检的 worker stdin 抢占

6.1 风险

主线程预检（_is_parallel_safe）跑一次 guardrail.check_argv。worker 线程（_handle_tool_use）再跑一次同样的 check。

guardrail.check_argv 是确定性的吗？取决于 llm_reviewer：

# safety/guardrail.py:117
if self.llm_reviewer is not None:
    try:
        reviewed = self.llm_reviewer(cmdline)   # 调外部 LLM · 非确定性
    except Exception as e:
        reviewed = None
        rationale.append(f"LLM 复审异常: {e!r}")  # 异常被吞
!
主线程预检 ALLOW，worker 线程内检可能 CONFIRM → worker 调 self.confirm(...) → CLI 的 stdin 被多 worker 抢 → "谁授权了什么"在审计链上错位。

6.2 两道防线

DEFENSE · 1
_is_parallel_safe 直接拒绝
if self.guardrail.llm_reviewer is not None: return False

只要 reviewer 启用，所有工具都不进并行路径。把「主线程预检 vs worker 内检」的不一致风险从源头切断。
DEFENSE · 2
_handle_tool_use worker 兜底
if threading.current_thread() is not threading.main_thread(): return [denied]

兜底：即便第一道因为某种原因失守，worker 拿到 CONFIRM 时立即 deny + 写 ERROR。

DORMANT
生产环境的并行路径完全 dormant。

7.2 为什么这样保守

1
preexec_fn 在 fork() 后子进程里执行任意 Python 回调
2
多线程父进程里 fork：glibc malloc 的内部锁可能被其它线程持有，子进程拿不到 → 死锁
3
信号处理器状态、TLS 状态可能不一致
4
resource.setrlimit 不是 async-signal-safe，理论上违规

这是 CPython 已知雷区（bpo-34037）。Python 3.12 起 subprocess 模块自身已优先用 posix_spawn 替代 fork（如果不需要 preexec_fn）；但只要传 preexec_fn，仍然走 fork。

7.3 设计意图

保留
并行路径代码 + 测试
gate 留在 supports_parallel_tool_execution 上
未来
切换到 posix_spawn
把 property 改成 True 就能开启
当前
baseline -34% 不依赖并行
暂时关掉并行不影响性能基线

def test_audit_event_serializes_shared_trace_updates(tmp_path):
    store = _BlockingStore()  # 第一次 append 时阻塞
    logger = AuditLogger(store, jsonl_file=...)

    def add_second():
        assert store.first_entered.wait(timeout=1)
        logger.event(trace, EventKind.LLM_THOUGHT, {"label":"second"})

9 ThreadPool 生命周期

agent/core.py:77
def _ensure_pool(self):
    if self._tool_pool is None:
        self._tool_pool = ThreadPoolExecutor(max_workers=4,
                                             thread_name_prefix="ky-tool")
    return self._tool_pool

def shutdown(self):
    if self._tool_pool is not None:
        self._tool_pool.shutdown(wait=False)
        self._tool_pool = None
1
懒创建：只在第一次走并行路径时才 new 一个 pool
2
max_workers=4：保守上限
3
thread_name_prefix：方便 trace 里看 "ky-tool-0" / "ky-tool-1"
4
shutdown(wait=False)：不等 worker 完成（调用方主动释放才该调）

正常路径下，ask() 返回时所有 worker 都已经收工，因为 fut.result() 会阻塞到 worker 完成。

10 当前并发路径的实际行为

ask("查 CPU 和磁盘")
  ↓
LLM 发起 2 个 tool_use: process_list + fs_df
  ↓
run_parallel = (
  True (Linux)
  and True (len >= 2)
  and False ← supports_parallel_tool_execution

  ↓
走串行 for 循环：
  _handle_tool_use(process_list) → done
  _handle_tool_use(fs_df) → done
  ↓
tool_results 顺序填好 → 灌回 LLM
FUTURE
所有并发安全机制（RLock、SQLite WAL 锁、JSONL 互斥、_is_parallel_safe、worker 兜底）当前都是为未来准备的。 测试用例通过 RecordingExecutor(supports_parallel_tool_execution=True) 绕过 C1 来覆盖并行路径——保证当未来切换到 posix_spawn 把 gate 打开时，并发不变量已经过测试。

11 关键不变量

1
self.confirm() 永远只在主线程调用：C2 两道防线 + tests/test_agent_parallel.py 验证
2
同一 trace 内事件落盘顺序 = seq 顺序：trace._lock + tests/test_audit.py 验证
3
不同 trace 之间事件可以并行写：每条 trace 独立锁
4
JSONL 关闭后 event() 不抛异常：H1 修复（fast-path + 锁内二次判空）
5
并行路径整体共进退：4 道 gate AND 关系，绝不"半并行"
6
生产环境当前不走并行：C1 gate 死，留作未来扩展
7
tool_results[idx] 顺序 = tool_uses[idx] 顺序：哪怕走并行也按 submit 顺序填
