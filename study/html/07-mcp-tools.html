service.py · _validate_unit · 两道防御
_FORBIDDEN_UNITS = {
    "systemd-logind", "systemd-journald", "systemd-udevd",
    "dbus", "dbus.service", "polkit", "polkit.service",
}

def _validate_unit(unit: str) -> str:
    if not unit or any(c in unit for c in [" ", ";", "|", "&", "$", "`"]):
        raise ToolError(f"非法 unit 名: {unit!r}")
    if unit.split(".")[0] in _FORBIDDEN_UNITS:
        raise ToolError(f"unit {unit!r} 在工具层禁用名单内（防误关核心服务）")
    return unit
!
没有 mask / disable / enable 工具——这些操作根本不暴露给 LLM。要做这些必须人工 SSH 上去。

filesystem.py · _safe_path · 三道防御
_PROTECTED_READ = {"/etc/shadow", "/etc/gshadow", "/etc/sudoers"}

def _safe_path(p: str) -> str:
    if not p:
        raise ToolError("path 不能为空")
    p = posixpath.normpath(p)
    if any(c in p for c in [";", "|", "&", "$", "`", "\n"]):
        raise ToolError(f"非法路径字符: {p!r}")
    if p in _PROTECTED_READ:
        raise ToolError(f"路径 {p} 在工具层禁读名单内")
    return p
!
fs_find 特别强制不走 -exec——argv 构造里根本没有 -exec，即便 LLM 输入也无法插入。同样禁了 -delete。

3 三层清洗的协作

工具调用从 LLM 到落地一共要过三层，每一层都是必要的纵深防御。

1
Tool.validate(args) — JSON Schema 类型 + required 校验
失败 → ToolError → 「工具参数非法」 · 防 LLM 给参数类型不对
2
Tool.build_argv(cleaned) — 工具自己的语义清洗
_safe_path · _validate_unit · shell-meta 黑名单 · 防工具自身的语义攻击
3
Guardrail.check_argv(argv) — 规则引擎 + 策略映射
系统级危险模式 · 决定 ALLOW/CONFIRM/DENY · 防工具组合在 OS 上的危险后果
4
ExecutionProxy.run(argv) — 落地
sudo + sandbox + Popen · 防执行环境本身（PATH / env / rlimit）
5
sudoers 白名单 — 最外层
即便所有层失守，sudo 仍按白名单兜底

4 ToolRegistry

def register(self, tool: Tool) -> None:
    if not tool.name:                    raise ValueError("Tool.name 不能为空")
    if tool.name in self._tools:         raise ValueError(f"工具名重复: {tool.name}")
    self._tools[tool.name] = tool

def to_mcp_list(self) -> list[dict]:        # 用于 MCP tools/list 响应（inputSchema）
    return [t.to_mcp() for t in self.all()]

def to_anthropic_tools(self) -> list[dict]: # 用于 Anthropic API（input_schema）
    return [{"name": t.name, "description": t.description,
             "input_schema": t.input_schema} for t in self.all()]
DIFF
两套序列化：MCP 用 inputSchema（camelCase）；Anthropic 用 input_schema（snake_case）。

5 MCP stdio JSON-RPC 服务器

MCP（Model Context Protocol）= Anthropic 提出的 LLM 工具接入协议。kyagent 实现了 stdio 传输（JSON-RPC 2.0 over stdin/stdout，newline-delimited）。

5.1 支持的方法

initialize
协议握手，返回 protocolVersion + capabilities
initialized
客户端确认握手完成（notification 无 id）
ping
心跳
tools/list
列出所有工具
tools/call
调用一个工具 — 核心方法

5.2 serve loop 特点

1
单线程串行：stdio 天然不能并发，所有调用顺序执行
2
解析错误不退出：单条 line 解析失败只回 -32700，继续读下一条
3
任何异常被包成 -32603：进程不会因为单次工具失败而崩
4
notification（无 id）不回包：_dispatch 返回 None 时不写

6 _call_tool · 核心方法

STEP 1 · 起 Trace
trace = Trace(user="mcp-client")
audit.open(trace) · trace.metadata = {channel:"mcp", tool: name}
STEP 2 · validate + build_argv
工具不存在 / 参数错 → isError 直接返回
写 ERROR 事件，但不抛异常
STEP 3
audit.event(TOOL_REQUEST)
{tool, argv, args, risk, requires_root}
STEP 4
guardrail.check_argv + SAFETY_CHECK
DENY → isError · CONFIRM → MCP 默认 deny
STEP 5
EXECUTION + executor.run + EXECUTION_RESULT
完整记录 argv / rc / stdout
STEP 6 · 关闭 Trace
audit.event(AGENT_REPLY) + audit.close(trace)
return {content:[{type:"text", text:out.content}], isError:not out.ok}

6.1 关键差异 vs Agent 主循环

DIFF · 1
不走 LLM
MCP 调用方就是 LLM 自己，没有「再请 LLM 决策」环节
DIFF · 2
CONFIRM = DENY
MCP 通道没法发起交互式 confirm，默认拒绝
DIFF · 3
每条 tools/call 独立 trace
每个工具调用都是独立审计单元

10 关键不变量

1
每个工具的 build_argv 必返回 list[str]：没有字符串、没有 shell
2
每个工具的 read_only 字段必须如实声明：影响 _is_parallel_safe
3
每个工具的 risk_level 是下限：永远只能向上抬，不能向下降
4
没有 raw shell 工具：所有工具都是受控的命令包装
5
每个 Tool 实例是无状态的：可以被并发 worker 共享
