2026-05-21 — Confirm 渲染层解耦重构（修复 P2 #2，治本而非补丁）

设计决策2026-05-21 引入 ConfirmRequest 协议
新增 kyagent/safety/confirm.py；改动 kyagent/safety/guardrail.py · intent.py · agent/core.py · cli.py · tests/test_agent_parallel.py

问题：reviewer 指出 core.py:182 在意图层 CONFIRM 路径把 IntentVerdict.to_dict() 喂给为 argv 层量身打造的 _cli_confirm， 后者读 h["description"] 而 IntentHit 不含此字段，导致异常被 except Exception 吞掉，用户从未被弹窗询问就被静默拒绝。

方案对比：

  • A 补丁（在 IntentHit 上硬塞 description 字段）：耦合方向反了，UI 反向决定业务层字段；以后 UI 增字段所有 verdict 都要改。
  • B 半解耦（写 _cli_confirm_intent 与 _cli_confirm_argv，调用方分支）：CLI 必须知道 verdict 种类，违反开闭原则。
  • C 真解耦（本次采用）：定义 ConfirmRequest 中间形态，每种 verdict 实现 to_confirm_request() 自我翻译；UI 与 Agent 仅依赖该协议，不再认识具体 verdict 类型。

实施要点：

  • ConfirmFn 签名从 (str, list[str], dict) → bool 改为 (ConfirmRequest) → bool。
  • Verdict.to_confirm_request(tool_name, argv)：title="tool {name}"，summary 用 rule_id (risk): description，body 是 argv。
  • IntentVerdict.to_confirm_request()：title="自然语言意图审查"，summary 用 rule_id (risk, category): matched，body 是 rationale。
  • 审计落盘格式（verdict.to_dict()）不变，trace 兼容；只有 UI 渲染入口被解耦。
  • 所有以 lambda *a, **k: False 兜底的旧调用点（bench / mcp / ask 子命令 / test_integration）天然兼容新签名，无需修改。
权衡2026-05-21 _auto_deny 保留为别名
kyagent/agent/core.py:58

core.py 原本定义 _auto_deny 私有函数；解耦后该函数迁到 confirm.py 成为 auto_deny。保留 _auto_deny = auto_deny 别名，避免任何 外部测试或 docs 中以 core._auto_deny 形式引用导致破坏。
